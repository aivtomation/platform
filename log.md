## [2026-09-09] bugfix & arch & deploy | Повна ліквідація дублювання публікацій (Deduplication & Concurrency Race Condition Safety)
- **Діагностика та аналіз першопричин дублювання:**
  - Виявлено, що при публікації через клієнтський кабінет (`chempion.agency@gmail.com`) виникало дублювання постів на важких платформах (YouTube, Instagram, Threads, Telegram).
  - Головні причини:
    1. Клієнтський polling у `index.php` кожні 2.5 с відправляв повторні запити `action=process_next` під час тривалої обробки відео.
    2. Видалення файлу замка (`unlink($lockFile)`) в `cron_poster.php` ламало роботу Linux `flock` (новий запит створював новий inode і отримував паралельний лок).

    4. 4-секундний цикл очікування в `flock` перетворював чергу запитів на лавиноподібний запуск нових воркерів після завершення попереднього кроку.

  - **Фронтенд (`index.php`):** Цикл `pollInterval` переведено у суворий режим **read-only** (`check_status=1`). Постійне спам-смикання `action=process_next` повністю видалено. Додано екстрений watchdog (спрацьовує виключно за умови повної відсутності прогресу протягом 60 секунд).
  - **Суворий неблокуючий м'ютекс (`cron_poster.php`):** Якщо завдання вже обробляється активним процесом, будь-який паралельний запит негайно повертає `already_processing` і завершується. Заборонено видалення lock-файлів (`unlink`) під час роботи для стабільності дескрипторів `flock`.
  - **Атомарна резервація платформи (`in_progress`):** Перед викликом API соцмережі платформа під ексклюзивним замком позначається як `processing` і записується в `jobs.json`. Інші процеси гарантовано ігнорують зарезервовану платформу.

### 2026-09-24: Виправлення зависання публікації в Instagram Reels та усунення оманливого статусу 100% у модальному вікні
- **Проблема:**

- **Діагностика першопричини (Root Cause Analysis):**
  1. **Бекенд-баг Meta Graph API (`MetaPoster.php`):**

     - На відміну від Threads API, Meta Graph API для Instagram **не підтримує** поля `error_message` та `error_subcode` на об'єктах контейнерів.
     - Meta Graph API повертала жорстку помилку: `HTTP 400: (#100) Tried accessing nonexisting field (error_message)`.
     - Через HTTP 400 умова `$stCode === 200` ніколи не виконувалася, і цикл опитування зависав на максимальні 120 ітерацій (10 хвилин), так і не викликавши фінальний крок публікації `media_publish`.

     - Після вичерпання таймауту опитування (`pollCount >= maxPollIterations`) або отримання завершального сигналу, перевірка `hasErrors` аналізувала лише ті платформи, які повернули помилку у `checkData.results`.
     - Оскільки Instagram ще висів у фоновому 10-хвилинному циклі й не мав запису в `results`, значення `hasErrors` залишалося `false`.
     - Фронтенд робив хибний висновок «якщо немає помилок у повернутих результатах, отже все успішно на 100%» і показував зелений бейдж успіху, хоча Instagram так і не було опубліковано.
